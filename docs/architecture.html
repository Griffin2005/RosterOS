Smart Roster Management System · Architecture v1

RosterOS Architecture

How the roster tool for a multi-brand CX operations team plans, solves, validates and publishes monthly rosters. Working rules and minimum coverage come from Google Sheets. A constraint solver builds the roster, and an independent rule engine checks it. Every gap it cannot close is explained to the operations manager instead of being hidden.

React + TypeScript FastAPI · Python 3.12 OR-Tools CP-SAT PostgreSQL 16 + replicas Redis streams Google Sheets API Claude tool-use assistant Docker · AWS ECS
Core decision

Optimise, then verify independently

The CP-SAT solver handles mandatory rules as hard constraints. It first proves the fewest possible coverage gaps, then optimises preferences without ever trading that coverage away. Shortfalls are reported, never silently dropped. A separate deterministic validator re-checks every roster, including manual edits, before it can be published.

02 · Scheduling engine

From rules to a verified roster

Two paths share the same verifier: a full monthly generation, and an incremental repair when something changes after publishing. The repair path keeps the rest of the roster frozen so people's plans don't shift.

Decision variables

  • work[e,d] ∈ {0,1}: employee e works on day d.
  • cover[e,s,d] ∈ {0,1}: e covers service line s (a brand × process pair) on d. Created only where e is assigned to s as primary or trained backup, and s operates on d.
  • slack[s,d] ∈ ℕ: missing heads for s on d. Never hidden: any value above zero becomes a C02 conflict.
  • off[e,d] = 1 − work[e,d] on days with no leave or holiday, which counts toward weekly offs.

Objective: lexicographic, two phases

Phase 1 minimise G = Σ slack[s,d] prove the fewest gaps Phase 2 fix Σ slack[s,d] ≤ G* keep that coverage minimise 500 · Σ changed[e,d] repair mode only + 80 · Σ backup_cover prefer primaries + 40 · (maxSun − minSun) fair Sundays / PH + 20 · Σ pref_off_viol. preferred off-days + 5 · Σ split_offs keep 2 offs adjacent

Phase 2 starts from phase 1's solution. Coverage always wins over a preferred off-day, as the brief requires, and this holds by construction rather than by weighting. If phase 2 runs out of time, the roster's coverage is still provably the best the rules allow. Phase 2 weights are stored in the solver_settings table, so they can be tuned without a deploy.

Single-resource vs multi-resource brands

The model treats both the same way, with no special branch. What differs is the data:

  • Single-resource brand (18 of 22): one employee holds every service line of the brand at a combined load ≤ 100%. Working that day covers all of them. Their weekly off must land on a day when none of the brand's lines operate, or a trained backup must step in. The pre-check flags brands with 7-day lines and no backup as at risk before solving starts.
  • Multi-resource brand (4 of 22): each line has its own assignees, so the solver staggers offs. For example, two people sharing CS at Urban Tandoor never take the same Sunday off when min_heads = 1 on Sundays.

Why CP-SAT and not greedy rules

  • Weekly offs are coupled across brands: moving one person's off can break three lines. CP-SAT reasons over all of them together.
  • Hard and soft rules sit in one model with explicit priorities, and the solver reports an optimality gap.
  • Solution hints from the previous roster plus a changed penalty give stable incremental repairs.
  • Every run records its status, objective, optimality gap and the rule-set version it used, so any roster can be re-checked against the rules it was built under.
  • Decomposition: people and lines interact only through assignments, so the model splits into connected components (East, West, and North+South, which a cross-pod backup links). Each is solved in turn with every worker.
  • Size: the sample month has about 4 000 booleans and proves optimal in 5–7 s on a laptop. On a single throttled vCPU, phase 1 still proves the coverage minimum. Before the two-phase model, the same host returned 16–22 false gaps.
03 · Data model

The service line is the unit of coverage

Coverage is never stored per brand. It is stored per service line (brand × process), because CS for a brand can run 365 days while its ACC line takes Sundays off. A brand's operating calendar and a person's working schedule are separate tables, as the brief asks.

Calendar ≠ schedule

CALENDAR_RULE says when a line must be staffed. ROSTER_DAY says when a person works. The solver connects them through H2 and H3, and nothing assumes they match.

Backups are data

A BACKUP assignment marks a trained, cross-brand fallback. The solver may use it at a cost (S-weight 80), and the recommender ranks backups first when it suggests fixes.

Everything versioned

Rule sets carry the Sheet revision they came from. Rosters carry the rule-set version they were solved under. If the sheet changes, affected rosters are marked stale and re-validated.

06 · Google Sheets integration

Rules come in, rosters go out

The ops team keeps working rules and minimum coverage in a Google Sheet they already know how to edit. The app pulls it, validates it and versions it. Published rosters are pushed to a separate dashboard workbook that mirrors the app's views. In the demo, a sheets-mock container serves the same API with seeded data.

Inbound: rules (pull)

  1. Drive Changes API is polled every 60 s; the sheet's revisionId is compared with the last import.
  2. Rows are parsed into Pydantic models; failures become C11 rows with cell references.
  3. The diff against the active rule set is shown to an admin. On accept, rule set vN+1 is written in one transaction.
  4. Rosters solved under vN are marked stale and re-validated, and new gaps are flagged.

Outbound: dashboards (push)

  • On publish, and on each validated edit (debounced 30 s), the worker writes tabs: Company, one per Pod, one per multi-person Brand, Coverage heatmap, Open conflicts.
  • One batchUpdate per tab; protected ranges keep the mirror read-only.
  • Idempotency key = roster id + version, so retries never duplicate rows.
  • The database is the source of truth for rosters. The Sheet is the source of truth only for rules.

08 · Roles & access levels

09 · Security

Controls by layer

The first row describes what this build implements and tests. The rows after it add the AWS production layers.

Accounts (implemented)

  • Argon2id password hashes (19 MiB, t=2); PBKDF2 hashes upgrade on sign-in
  • Policy: 12+ characters, mixed classes, no username, not common, no runs
  • Lockout after 5 failures; per-IP rate limit; identical errors for unknown users
  • No passwords in code or images: seeded accounts get theirs from deployment secrets at start-up

Sessions (implemented)

  • JWT holding only the account id and session version, in an httpOnly SameSite=Strict cookie (Secure in production)
  • CSRF token bound to the session on every write
  • Session version bumps on password change, reset, role change or deactivation, which ends older sessions at once
  • Temporary passwords must be replaced before any other call succeeds

Team & HTTP (implemented)

  • Nobody grants a role at or above their own; the last active super admin is protected
  • CSP, HSTS, frame-ancestors none, nosniff, Referrer- and Permissions-Policy
  • API docs off in production; startup refuses weak secrets
  • Exports scoped, audited and protected against formula injection

Identity (AWS)

  • Cognito user pool; MFA required for Admin and Ops roles
  • 15-min access tokens, rotating refresh tokens
  • Role and scope re-checked against the database on every request

Network

  • DB and Redis in isolated subnets, no internet route
  • Security groups allow only API → DB, workers → Redis
  • WAF managed rules + per-IP rate limit at CloudFront
  • Egress to Google and Anthropic through NAT only

Data

  • KMS encryption at rest for RDS, S3, Redis, backups
  • TLS 1.2+ on every hop, including DB connections
  • No contact data stored; client IPs kept only as keyed hashes
  • Leave reasons limited to the employee, their pod lead and managers
  • Row-level security mirrors the RBAC scope

Secrets & keys

  • Secrets Manager with rotation; nothing in images or env files
  • Google access through Workload Identity Federation from the AWS task role, so no long-lived service-account key
  • NAS backups encrypted with a key held offline

AI data handling

  • Names are replaced with employee codes before any request leaves the server, and restored only in the reply shown to the reader
  • Tool calls run with the caller's scope
  • Each query is rate limited per user and audited (mode and tools used) without its content

Supply chain & audit

  • Pinned base images, non-root containers, read-only root FS
  • ECR scan on push; CI blocks critical CVEs
  • Append-only audit_event + CloudTrail; S3 Object Lock on backups
10 · AI admin assistant

Explains and proposes, never publishes

A Claude-powered chat panel for Ops Managers and Admins. It answers questions like "who covers Urban Tandoor CS on the 25th?" and "why is Kesar Kitchen red on Sunday?", and it can try what-if changes in a sandbox. Every action it takes goes through the same API, permissions and validator as a human edit.

ToolTypeWhat it does
get_coverage(scope, from, to)READHeads vs required per line and day for a pod, brand or process
list_conflicts(roster, severity)READOpen conflicts with structured explanations
explain_slot(line, date)READWho is assigned and why each person is or isn't available (leave, H4 load, H7 streak…)
suggest_backups(line, date)READRanked candidates from the backup recommender, with cost and violated rules
what_if(changes[])SANDBOXRuns a repair solve on a copy; returns diff, new conflicts and objective change
draft_change_request(changes[], reason)PROPOSALCreates a pending change for a human to approve or reject

Not exposed to the assistant: publish, delete, master-data edits, user administration and rule-set import. Model: claude-opus-5-5 via the Messages API with tool use and server-side refusal fallbacks, hosted inside the API service so the tools run with the caller's permissions. If the API is unavailable, the conflict panel still shows the validator's own templated explanations.
